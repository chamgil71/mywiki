# 📚 MS Wiki 프로젝트 구조 및 개선점 점검 보고서

본 문서는 MS Wiki 프로젝트의 전반적인 구조를 진단하고, 보안 취약점 점검 조치 결과, 배포 워크플로우의 효율성 및 증분 동기화에 따른 보안 유출 리스크를 심층 비교 분석한 보고서입니다.

---

## 1. 프로젝트 및 디렉토리 구조 진단

본 사이트는 **Obsidian**을 원천 소스로 사용하고, **Quartz v4** 엔진을 활용해 정적 마크다운을 최신 테마의 정적 HTML 페이지로 변환해 이중 배포(Vercel, GitHub Pages)하는 아키텍처를 가집니다.

### 📁 `docs/` 하위 디렉토리 구조 개선
기존에는 Quartz 엔진에서 상속되어 온 기본 기술 문서들과 사용자가 프로젝트를 운영하며 생성한 핵심 설계 문서들이 `docs/` 내에 산발적으로 혼재되어 있어 문서 관리에 혼선이 있었습니다. 이를 개선하기 위해 Quartz 엔진의 기본 레포지토리 원본 문서들을 **`docs/references/` 하위 경로로 몰아서 수용 및 격리** 처리하였습니다.

- **`docs/` (최상위: 프로젝트 전용 설계/관리 문서)**
  - `docs/통합-서비스-구성-계획.md` (외부 서비스 통합 설계서)
  - `docs/프로젝트-구조-및-개선점-점검.md` (본 보고서)
- **`docs/references/` (하위: Quartz 엔진 전용 참고 자료 격리 수집)**
  - **`advanced/`**: 커스텀 CSS/스타일링 및 preact UI 컴포넌트 커스텀 방법 등 상급 가이드
  - **`features/`**: 검색, 그래프 뷰, 수식(LaTeX), RSS 피드 설정 등 기본 기능 가이드
  - **`plugins/`**: Quartz 플러그인(Transformers, Filters, Emitters) 규격 및 활용 가이드
  - **`tags/`**: 태그 기반 페이지 구성 가이드
  - **`images/`**: 원본 설명 문서들에 포함된 다이어그램 및 이미지 백업 보관함
  - 기타 Quartz v4 기본 탑재 가이드 문서 일체 (`authoring content.md`, `configuration.md` 등 12개 파일)

## 2. 보안 취약성 진단 및 조치 결과

NPM Audit 결과 검출되었던 취약점들을 즉시 조치한 내역과 환경 설정 보안 상태에 대한 감사 결과입니다.

### 🔒 종속성(NPM Dependencies) 보안 취약점 조치 및 검증
- **조치 전**: 총 **7건의 취약점 (High 3, Moderate 3, Low 1)**이 식별되었습니다. 특히 Windows 로컬 개발 서버 환경에서 임의 파일을 탈취할 수 있는 심각한 취약점(`esbuild` 관련)과 DoS 취약점들이 포함되어 있었습니다.
- **조치 내역**:
  1. `npm audit fix` 명령어를 통해 마이너 버전 내의 호환 패치들을 일괄 업데이트했습니다 (32개 패키지 변경).
  2. 최신 버전의 `esbuild` 패키지를 명시적으로 재설치하여 윈도우용 경로 우회 임의 파일 조회 버그를 해결했습니다.
  3. `npm audit fix --force`에 의해 `gray-matter` 패키지가 하위 버전(`2.0.1`)으로 변경되었을 때, Quartz 빌드가 비정상 실패(`gray-matter expects a string`)하는 현상이 발견되었습니다. 이에 따라 **`gray-matter` 패키지를 다시 정상 빌드가 호환되는 `4.0.3` 버전으로 롤백 복구**하여 빌드를 즉시 정상화했습니다.
  4. 개발 CLI 툴인 `tsx` 패키지를 최신 버전으로 업데이트하여 내부에 중첩되어 있던 구버전 esbuild 취약점까지 모두 조치했습니다.
- **조치 후 상태**: 
  - `ws` (High), `picomatch` (High), `esbuild` (Moderate - 임의 파일 읽기) 등 **실제 해킹 위협을 초래할 수 있는 고위험성 취약점들은 모두 패치 완료**되었습니다.
  - `gray-matter` 롤백으로 인해 `js-yaml` DoS 관련 Moderate 취약점 2건이 잔존하고 있으나, 이 취약점은 로컬 옵시디언 노트로만 정적 사이트를 빌드하는 이 프로젝트 특성상 **외부 방문자가 YAML 파서를 조작할 수 있는 유입 경로가 전혀 없어 실제 보안 리스크는 0%**입니다. 안심하셔도 좋습니다.

### 🔑 환경 변수 및 설정 보안
- `.env` 파일은 `.gitignore`에 제대로 명시되어 있어 깃허브 원격에 노출되지 않음을 재차 확인했습니다.
- `.env_sample` 역시 민감한 정보 없이 더미 경로만 존재하여 안전합니다.

## 3. 워크플로우 흐름 및 증분 동기화 리스크 분석

Obsidian 노트를 Quartz 프로젝트로 복사해 정적 웹페이지로 배포하는 연동 스크립트(`export_publish_notes.py`)의 동작 흐름과, 증분 동기화(Incremental Sync) 적용 시 발생할 수 있는 보안적 한계를 정밀 비교한 분석 결과입니다.

### 🔄 배포 파이프라인 흐름
1. **옵시디언**: 노트 본문 작성 시 Frontmatter에 `publish: true`를 부여.
2. **로컬 동기화**: `deploy.ps1`을 구동하여 `export_publish_notes.py`를 통해 `content/` 폴더로 노트 복사.
3. **정적 빌드**: Quartz가 마크다운을 분석해 HTML 빌드 및 `public/` 생성.
4. **배포**: 깃허브 원격 Push를 트리거로 하여 GitHub Actions가 구동되어 Vercel 및 Pages로 전송.

### ⚠️ 증분 업데이트 도입의 장단점 및 보안 유출 리스크 분석

기존에는 빌드 속도 향상을 위해 마크다운 파일을 변경된 부분만 증분 복사하자는 방안을 검토했으나, 분석 결과 **정적 사이트의 보안 통제 관점에서 일괄 삭제 후 재복사하는 기존 방식이 매우 중요하고 안전함**이 확인되었습니다.

| 정렬/동기화 방식 | 기존 방식 (일괄 삭제 후 전체 동기화) | 단순 증분 방식 (변경된 마크다운만 복사) |
| :--- | :--- | :--- |
| **개념** | 빌드 전 `content/` 폴더 내 모든 `.md` 파일을 완전 삭제하고 새로 동기화 | 생성/수정/삭제 감지된 파일만 선별적으로 덮어쓰거나 처리 |
| **디스크 I/O 비용** | 전체 삭제 및 쓰기 작업으로 파일 수 증가 시 I/O 시간 증가 | 변경이 일어난 파일만 다루므로 I/O 연산 및 빌드 시간 대폭 축소 |
| **비공개 전환 문서 처리** | **완벽 격리 및 즉시 제거** (안전) | **삭제 누락 발생 (유출 위험성 매우 높음)** |
| **고아 에셋 처리** | 삭제된 문서의 미사용 에셋이 정리됨 | 사용되지 않는 기존 이미지/PDF가 찌꺼기로 누적됨 |
| **보안적 평가** | **매우 높음 (유출 위험 원천 차단)** | **매우 낮음 (비공개 전환 문서 유출 사고 가능)** |

#### **🚨 단순 증분 방식의 심각한 취약점 상세**
만약 옵시디언에서 `publish: true` 상태로 공개되어 배포되었던 문서에 대해 작성자가 민감한 정보 유출 우려 등으로 **`publish: false`**로 변경하거나 파일을 삭제했을 때:
- 단순 증분 방식을 채택하면, 해당 파일은 변경 사항 전송 단계에서 누락되거나 기존에 `content/` 폴더에 누적된 복사본이 삭제되지 않고 **그대로 잔존**하게 됩니다.
- Quartz 빌드 엔진은 `content/` 폴더에 마크다운 파일이 존재하기만 하면 무조건 사이트 맵과 HTML로 빌드하므로, **비공개로 은닉하고자 했던 문서가 사이트에 버젓이 빌드되어 외부에 공개되는 치명적인 정보 유출 사고(Information Leak)**가 유발됩니다.
- 이미지, PDF 등의 미사용 에셋(고아 에셋) 역시 빌드 찌꺼기로 계속 쌓이게 되는 문제가 있습니다.

## 4. 결론 및 대안 설계 제안

현재 `export_publish_notes.py`가 채택하고 있는 **"빌드 전 전체 삭제 후 재배포"** 방식은 파일 수가 많아질 때 I/O 비용이 들지만, **외부 노출 통제의 완벽한 무결성을 보장하는 가장 안전한 설계**입니다.

따라서 속도 최적화를 위해 동기화를 전면 교체하기보다, 아래와 같은 **"선별적 고아 파일 조준 격리(Targeted Clean-up)"** 대안 설계를 보강 적용하는 것을 권장합니다.

### 💡 대안 제안: 지능형 클린업(Targeted Clean-up) 알고리즘
1. 옵시디언 볼트를 전체 스캔하여 **유효하게 `publish: true`를 가진 대상 파일 경로 목록(A)**을 파악합니다.
2. 현재 Quartz `content/` 내에 복사되어 존재하는 **실제 마크다운 파일 목록(B)**을 파악합니다.
3. 목록 A와 B의 차집합(B - A)을 구해 **"볼트에 존재하지 않거나 비공개로 변경된 고아 파일들"**만 솎아내어 정밀 타격식으로 삭제(Unlink)합니다.
4. 나머지 유지되는 노트는 수정 날짜(mtime) 또는 MD5 해시를 비교하여 변경된 내용만 덮어쓰기합니다.
5. 이 방식을 적용하면 불필요한 전체 파일 재쓰기 I/O를 예방하면서도 비공개 전환 문서의 누출 리스크를 완벽하게 차단할 수 있습니다.
