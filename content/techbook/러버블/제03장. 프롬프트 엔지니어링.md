# 제3장. 프롬프트 엔지니어링 — 러버블과 대화하는 법

> _"AI는 당신이 알려준 것만큼만 이해한다. 프롬프트는 단순한 명령이 아니라 AI와 나누는 설계 대화다."_

---

## 0) 연결 고리

> 🔗 2장에서 러버블의 인터페이스와 첫 앱 생성을 경험했습니다. 이제 AI에게 원하는 결과를 정확하게 전달하는 기술, 즉 **프롬프트 엔지니어링(Prompt Engineering)** 을 익힐 차례입니다. 러버블을 잘 쓰는 것과 못 쓰는 것의 차이는 결국 프롬프트의 품질에서 갈립니다.

---

## 3.1 좋은 프롬프트의 3요소 — 목적·맥락·제약

### 1) 개념 정의 및 필요성

러버블 AI는 사용자가 입력한 프롬프트를 바탕으로 코드를 생성합니다. 이때 AI는 당신의 머릿속을 읽을 수 없습니다. **오직 당신이 입력한 텍스트만을 근거로 코드를 만듭니다.**

좋은 프롬프트와 나쁜 프롬프트의 차이는 아래 예시에서 극명하게 드러납니다:

|구분|프롬프트|결과|
|---|---|---|
|❌ 나쁜 예|"대시보드 만들어줘"|AI가 임의로 레이아웃·기능·색상을 결정. 원하는 것과 다를 가능성 90%|
|✅ 좋은 예|"전자상거래 관리자용 대시보드를 만들어 주세요. 주문 현황, 재고 수량, 고객 문의 수를 카드형 위젯으로 상단에 배치하고, 최근 7일간 매출 추이를 선 그래프로 하단에 표시해 주세요. 색상은 네이비(#1E3A5F)와 흰색 기반으로 합니다."|의도에 부합하는 구체적인 결과 생성|

---

### 2) 좋은 프롬프트의 3요소

좋은 프롬프트는 언제나 세 가지 요소를 포함합니다.

```
┌─────────────────────────────────────────────────────┐
│                좋은 프롬프트의 3요소                   │
├──────────────┬──────────────────────────────────────┤
│  ① 목적      │ 무엇을 만들고 싶은가? (What)           │
│  (Purpose)   │ → 기능, 페이지, 컴포넌트를 명확히 지정  │
├──────────────┼──────────────────────────────────────┤
│  ② 맥락      │ 왜, 누구를 위해? (Context)             │
│  (Context)   │ → 사용자 유형, 비즈니스 목적, 기존 구조 │
├──────────────┼──────────────────────────────────────┤
│  ③ 제약      │ 건드리면 안 되는 것은? (Constraint)    │
│  (Constraint)│ → 수정 금지 파일, 유지할 디자인, 범위  │
└──────────────┴──────────────────────────────────────┘
```

**① 목적(Purpose) — What을 명확히**

막연한 단어 대신 구체적인 기능과 동작을 기술합니다.

- ❌ "회원가입 페이지"
- ✅ "이메일+비밀번호 회원가입 폼을 만들어 주세요. 이름, 이메일, 비밀번호(8자 이상), 비밀번호 확인 필드가 필요합니다. 가입 완료 시 `/dashboard`로 이동합니다."

**② 맥락(Context) — 왜, 누구를 위해**

AI는 프로젝트의 전체 맥락을 모릅니다. 특히 **새 기능을 추가할 때는 기존 구조를 언급**해 주어야 합니다.

- ❌ "결제 페이지 추가해줘"
- ✅ "기존의 `/cart` 페이지에서 '결제하기' 버튼을 클릭하면 이동하는 `/checkout` 페이지를 추가해 주세요. 현재 `useCart` 훅에 장바구니 데이터가 있습니다."

**③ 제약(Constraint) — 건드리면 안 되는 것**

러버블 AI는 의욕이 넘쳐서 관련 없는 파일까지 수정하는 경향이 있습니다. 범위를 명확히 제한하면 이를 방지할 수 있습니다.

- ✅ "헤더 네비게이션에 '알림' 아이콘을 추가해 주세요. `/src/components/ui/` 폴더의 기존 컴포넌트는 수정하지 마세요."

> ⚠️ **WARNING**
> 
> 러버블 AI가 예상치 못한 파일을 수정하는 것을 **"콜래터럴 에딧(Collateral Edit)"** 이라고 부릅니다. 이는 복잡한 프로젝트에서 자주 발생하는 문제입니다. 프롬프트에 항상 **"~는 수정하지 마세요"** 라는 제약 조건을 포함시키는 습관을 들이세요. 특히 공유 레이아웃(`Layout.tsx`), 공통 훅(`useAuth.ts` 등)은 반드시 보호해야 합니다.

---

### 3) 프롬프트 품질 자가 진단 체크리스트

프롬프트를 전송하기 전에 다음 항목을 확인하세요:

- [ ] 어떤 **페이지/컴포넌트**에서 작업하는지 명시했는가?
- [ ] 기능의 **입력(Input)과 출력(Output)**을 설명했는가?
- [ ] 기존 코드와의 **연결 관계**를 언급했는가? (어떤 훅/API를 사용하는지)
- [ ] **수정하면 안 되는 부분**을 명시했는가?
- [ ] 한 번에 **3~5개 이하**의 변경 사항만 요청했는가?

## 3.2 초기 프롬프트 설계 전략 — PRD 방식 활용

### 1) 개념 정의 및 필요성

새 프로젝트를 시작할 때 입력하는 **첫 번째 프롬프트(Initial Prompt)** 는 가장 중요합니다. 첫 프롬프트가 프로젝트의 전체 구조와 방향성을 결정하기 때문입니다.

이때 가장 효과적인 방법은 **PRD(Product Requirements Document, 제품 요구사항 문서)** 형식을 활용하는 것입니다.

> 📝 **NOTE**
> 
> PRD는 원래 소프트웨어 팀이 개발 전에 작성하는 공식 기획 문서입니다. 러버블에서는 이 형식을 **AI에게 프로젝트 전체를 한 번에 이해시키는 도구**로 활용합니다. 완벽한 문서가 필요한 것이 아니라, AI가 일관된 방향으로 작업하도록 충분한 맥락을 제공하는 것이 목적입니다.

---

### 2) PRD 기반 초기 프롬프트 템플릿

다음 구조를 복사하여 새 프로젝트 시작 시 활용하세요:

```
## 프로젝트 개요
[앱의 이름과 한 줄 설명을 작성합니다]
예: "TaskFlow — 소규모 팀을 위한 프로젝트 관리 SaaS 서비스"

## 핵심 사용자(Target User)
[주요 사용자가 누구인지 설명합니다]
예: "5~20명 규모의 스타트업 팀. 기술 지식이 없는 PM도 쉽게 사용 가능해야 합니다."

## 핵심 기능(Core Features)
[반드시 있어야 할 기능을 나열합니다]
1. 이메일/Google 로그인 및 회원가입
2. 프로젝트 생성·수정·삭제
3. 칸반 보드(Kanban Board)로 태스크 관리
4. 팀원 초대 및 역할(Admin/Member) 구분
5. 태스크 완료 시 담당자에게 이메일 알림

## 기술 스택 요구사항
- 프론트엔드: React + TypeScript + Tailwind CSS
- 백엔드: Supabase (DB + Auth + Storage)
- UI 라이브러리: shadcn/ui

## 디자인 방향
[원하는 스타일을 설명합니다]
예: "깔끔한 미니멀 디자인. 메인 색상 `#2563EB`(파랑), 보조 색상 `#F8FAFC`(연한 회색). 
     Notion과 Linear의 중간 느낌."

## 스코프 밖(Out of Scope — 이번 버전에서 제외)
- 결제/구독 기능
- 모바일 앱 (웹 반응형만 지원)
- 파일 첨부 기능

## 시작 요청
위 내용을 바탕으로 프로젝트의 기본 구조와 메인 랜딩 페이지부터 
만들어 주세요. 아직 Supabase는 연동하지 않아도 됩니다.
```

> 💡 **TIP**
> 
> **ChatGPT나 Claude를 활용해 PRD를 먼저 작성하세요.** "나는 ~한 서비스를 만들고 싶다. 러버블용 PRD 초기 프롬프트를 작성해 줘"라고 요청하면 위 템플릿에 맞는 초안을 빠르게 얻을 수 있습니다. 이 방법으로 초기 프롬프트 작성 시간을 10분 이내로 줄일 수 있습니다.

### 3) PRD 기반 초기 프롬프트 실전 예시

다음은 실제로 사용 가능한 초기 프롬프트 완성 예시입니다:

```
## 프로젝트 개요
DocSense — PDF·문서를 업로드하면 AI가 요약·분석해 주는 SaaS 서비스

## 핵심 사용자
업무 문서가 많은 직장인, 리서치가 많은 대학원생.
비개발자도 직관적으로 사용 가능해야 합니다.

## 핵심 기능
1. 이메일 + Google OAuth 로그인/회원가입
2. PDF·TXT 파일 업로드 (최대 10MB)
3. 업로드된 문서 목록 관리 (삭제·재분석 가능)
4. AI 문서 요약 (300자 이내)
5. 문서에 대한 Q&A 채팅 인터페이스
6. 무료(3회/월) / Pro(무제한) 플랜 구분

## 기술 스택
- React + TypeScript + Tailwind CSS + shadcn/ui
- Supabase (Auth + Storage + DB)
- OpenAI API는 나중에 연동 예정 (지금은 목업)

## 디자인 방향
모던하고 신뢰감 있는 느낌. 메인 색상: 인디고(#4F46E5).
Notion과 유사한 좌측 사이드바 레이아웃.

## Out of Scope
- 모바일 앱, 팀 협업, 음성 인식

## 시작 요청
랜딩 페이지(/)와 로그인(/login), 회원가입(/register) 페이지,
그리고 로그인 후 보이는 대시보드(/dashboard) 기본 레이아웃(사이드바 포함)을
먼저 만들어 주세요. Supabase 연동은 아직 하지 않아도 됩니다.
```

## 3.3 반복 수정 프롬프트 패턴 16선

초기 프롬프트로 기본 구조를 만든 후에는 반복적인 수정 프롬프트로 앱을 완성해 나갑니다. 자주 사용되는 16가지 패턴을 상황별로 정리했습니다.

### 1) 기능 추가 패턴 (4선)

**패턴 1: 새 페이지 추가**

```
/profile 페이지를 추가해 주세요.
- 표시 항목: 프로필 사진, 이름, 이메일, 가입일
- 프로필 사진은 클릭하면 파일 업로드 가능
- 이름은 인라인 편집(클릭 후 수정) 가능
- 기존 헤더 네비게이션에 '프로필' 링크 추가
- useAuth 훅의 user 객체 데이터를 사용할 것
```

**패턴 2: 기존 페이지에 컴포넌트 추가**

```
/dashboard 페이지 상단에 통계 카드 4개를 추가해 주세요.
- "총 문서 수", "이번 달 분석 수", "잔여 크레딧", "마지막 접속"
- 각 카드는 아이콘(lucide-react), 수치, 라벨로 구성
- 현재 페이지의 레이아웃과 색상을 유지할 것
- /src/components/ui/ 폴더의 기존 파일은 수정하지 말 것
```

**패턴 3: 검색 기능 추가**

```
문서 목록 페이지에 검색 기능을 추가해 주세요.
- 입력창은 목록 상단에 배치
- 파일 이름과 요약 내용을 대상으로 실시간(입력 즉시) 필터링
- 검색 결과가 없을 경우 "검색 결과가 없습니다" 메시지 표시
- 기존 documents 배열 상태(state)를 활용할 것
```

**패턴 4: 정렬·필터 기능 추가**

```
문서 목록에 정렬 옵션을 추가해 주세요.
- 정렬 기준: 최신순, 오래된 순, 이름 오름차순, 이름 내림차순
- shadcn/ui의 Select 컴포넌트 사용
- 검색 기능 오른쪽에 배치 (기존 검색 UI 변경하지 말 것)
```

---

### 2) 스타일·UI 수정 패턴 (4선)

**패턴 5: 전체 색상 테마 변경**

```
앱의 주요 색상을 현재 파란색에서 에메랄드 그린(#10B981)으로 변경해 주세요.
- 버튼, 링크, 활성 상태 표시, 테두리 강조색 모두 변경
- tailwind.config.ts의 primary 색상 설정도 함께 업데이트
```

**패턴 6: 반응형 수정**

```
현재 대시보드가 모바일(375px)에서 깨집니다.
모바일 퍼스트(Mobile-First)로 반응형을 수정해 주세요.
- 사이드바는 모바일에서 숨기고 햄버거 메뉴 버튼으로 열고 닫기
- 통계 카드 4개는 모바일에서 2열로 배치
- 테이블은 모바일에서 카드 형태로 변환
- shadcn/ui와 tailwind 기본 브레이크포인트(sm, md, lg) 사용
```

**패턴 7: 로딩 상태 개선**

```
API 호출 중 로딩 상태를 개선해 주세요.
- 문서 목록 로딩 시 스켈레톤(Skeleton) UI 표시 (shadcn/ui Skeleton 컴포넌트 활용)
- 버튼 클릭 후 처리 중일 때 버튼 내부에 스피너 아이콘 표시 및 비활성화
- 기존 로딩 스피너가 있다면 제거하고 위 방식으로 통일
```

**패턴 8: 다크 모드 추가**

```
다크 모드(Dark Mode)를 추가해 주세요.
- 헤더 우측에 라이트/다크 토글 버튼 추가
- tailwind의 dark: 클래스를 활용
- 사용자 선호 모드는 localStorage에 저장하여 새로고침 후에도 유지
- 모든 페이지에 일관되게 적용
```

### 3) 버그 수정 패턴 (4선)

**패턴 9: 오류 메시지 기반 수정**

```
다음 오류가 발생합니다. 수정해 주세요.

오류 메시지:
TypeError: Cannot read properties of undefined (reading 'map')
  at DocumentList (/src/components/DocumentList.tsx:24:28)

상황: 문서 목록 페이지에서 처음 로드할 때만 발생합니다.
원인으로 예상되는 것: documents 배열이 undefined인 상태에서 .map()을 호출하는 것 같습니다.
```

**패턴 10: 특정 동작 버그 수정**

```
/dashboard 페이지에서 버그가 있습니다.

재현 순서:
1. 문서를 삭제한다
2. 바로 다른 문서를 클릭한다
3. 삭제된 문서의 내용이 잠깐 표시된 후 사라진다

예상 동작: 삭제 후 목록이 즉시 업데이트되어야 함
/src/components/DocumentList.tsx와 useDocuments 훅을 확인해 수정해 주세요.
```

**패턴 11: AI 루프 탈출 프롬프트**

```

코드를 수정하기 전에 먼저 문제의 근본 원인(Root Cause)을
```

**패턴 12: 코드 품질 개선**

```
역할 정의:
```

## 3.4 Knowledge 설정 활용 — AI에게 프로젝트 컨텍스트 고정시키기

### 1) 개념 정의 및 필요성

**Knowledge(지식 베이스)** 는 러버블 AI에게 프로젝트의 고정 컨텍스트를 제공하는 설정입니다. Knowledge에 입력한 내용은 **매번 프롬프트를 전송할 때마다 자동으로 AI에게 함께 전달**됩니다.

> 📝 **NOTE**
> 
> 러버블 공식 문서는 Knowledge를 "프로젝트의 두뇌(Brain)"라고 설명합니다. AI는 대화가 길어질수록 초반 맥락을 잊어버리는 경향이 있습니다. Knowledge는 이 문제를 해결하여 프로젝트 전반에 걸쳐 AI가 일관된 방향으로 작업하도록 합니다.

---

### 2) Knowledge 설정 방법

1. 프로젝트 에디터 상단 **설정(⚙️) 아이콘** 클릭
2. **"Knowledge"** 탭 선택
3. 텍스트 에디터에 프로젝트 컨텍스트 입력
4. **저장** — 이후 모든 프롬프트에 자동 포함

---

### 3) Knowledge에 포함할 내용 (권장 템플릿)

```markdown
## 프로젝트 기본 정보
- 서비스명: DocSense
- 목적: PDF 문서 AI 분석 서비스
- 주요 사용자: 문서 업무가 많은 직장인, 대학원생

## 기술 스택
- 프론트엔드: React 18 + TypeScript + Vite
- UI: Tailwind CSS + shadcn/ui
- 백엔드: Supabase (PostgreSQL + Auth + Storage)
- 라우팅: React Router v6

## 디자인 원칙
- 주요 색상: 인디고 #4F46E5 (primary), 슬레이트 #F8FAFC (background)
- 폰트: 시스템 폰트 (한국어 지원 필수)
- 반응형: 모바일 퍼스트, tailwind sm/md/lg 브레이크포인트 사용
- 다크 모드: 지원하지 않음

## 코딩 규칙
- 컴포넌트는 /src/components/ 아래 기능별 폴더로 분류
- 공통 훅은 /src/hooks/ 폴더
- Supabase 쿼리는 /src/integrations/supabase/ 폴더에서만 작성
- 모든 TypeScript 인터페이스는 /src/types/ 폴더에 정의

## 현재 데이터 구조 (Supabase 테이블)
- users: id, email, role, created_at
- documents: id, user_id, title, file_url, summary, created_at
- analyses: id, document_id, question, answer, created_at

## 수정 금지 파일
- /src/components/ui/ (shadcn/ui 기본 컴포넌트)
- /src/lib/utils.ts
- /src/integrations/supabase/client.ts

## 언어 설정
- 모든 UI 텍스트는 한국어로 작성
- 에러 메시지도 한국어로 표시
- 코드 주석은 한국어 또는 영어 모두 허용
```

> 💡 **TIP**
> 
> **Plan Mode로 Knowledge를 자동 생성할 수 있습니다.** 프로젝트 작업을 어느 정도 진행한 후 Chat Mode에서 다음 프롬프트를 입력하세요: "지금까지 구현된 기능을 기반으로 이 프로젝트의 Knowledge 파일을 작성해 줘." AI가 현재 코드베이스를 분석하여 Knowledge 초안을 자동으로 만들어 줍니다.

### 4) Knowledge 업데이트 시점

Knowledge는 살아있는 문서입니다. 다음 상황에서 반드시 업데이트하세요:

|업데이트 시점|업데이트 내용|
|---|---|

|디자인 시스템 변경 시|디자인 원칙 섹션 갱신|
|프로젝트 방향 전환 시|프로젝트 기본 정보 갱신|

## 3.5 ChatGPT / Claude로 프롬프트 사전 설계하기

### 1) 외부 AI를 활용한 프롬프트 설계 워크플로우

러버블의 크레딧을 절약하면서 더 정교한 프롬프트를 만드는 방법은 **외부 AI를 브레인스토밍 파트너로 활용**하는 것입니다.

```
[워크플로우]

① ChatGPT 또는 Claude에서 아이디어 구체화
        ↓
② 기능 명세·데이터 구조·UI 레이아웃 논의
        ↓
③ PRD 초안 또는 상세 프롬프트 작성 요청
        ↓
④ 완성된 프롬프트를 러버블에 붙여넣기
        ↓
⑤ 결과 검토 → 필요 시 다시 ①로
```

### 2) ChatGPT / Claude 활용 프롬프트 예시

**PRD 작성 요청:**

```
나는 러버블(Lovable.dev)로 [서비스 설명]을 만들려고 합니다.
러버블용 초기 프롬프트 형식(PRD 방식)으로 작성해 주세요.

포함 항목:
1. 프로젝트 개요
2. 핵심 사용자
3. 핵심 기능 목록
4. 기술 스택 (React + TypeScript + Supabase + Tailwind CSS 기반)
5. 디자인 방향
6. Out of Scope
7. 시작 요청 (랜딩 페이지와 인증 페이지부터 시작)
```

**데이터베이스 설계 요청:**

```
다음 기능을 가진 앱의 Supabase(PostgreSQL) 데이터베이스 스키마를 설계해 주세요:
[기능 목록]

각 테이블에 대해 컬럼명, 타입, 제약조건, 외래키 관계를 포함해 주세요.
러버블에 붙여넣을 수 있는 프롬프트 형식으로 작성해 주세요.
```

> 📝 **NOTE**
> 
> Claude는 긴 문서 분석과 구조화된 출력에 강점이 있어 PRD 작성에 유리합니다. ChatGPT(GPT-4o)는 창의적인 기능 아이디어 브레인스토밍에 유리합니다. 두 도구를 상호보완적으로 활용하는 것이 가장 효율적입니다.

## 3.6 흔한 실수와 크레딧 낭비 방지법

### 1) AI 루프(AI Loop)란?

같은 버그를 고치려고 AI에게 반복 요청하면 AI가 수정을 시도할 때마다 다른 곳을 망가뜨리는 악순환에 빠지는 현상을 **AI 루프**라고 합니다. 이는 러버블 사용자가 가장 많이 겪는 고통입니다.

```
[AI 루프 발생 패턴]

버그 발견
    ↓
"이 버그 고쳐줘" → AI가 수정 시도
    ↓
다른 곳이 망가짐
    ↓
"이게 또 망가졌어" → AI가 수정 시도
    ↓
다시 처음 버그 재발
    ↓
(반복... 크레딧 소진)
```

---

### 2) AI 루프 방지 및 탈출 전략

**예방 전략 — Pin(버전 고정) 활용**

기능이 완성될 때마다 해당 버전을 **Pin**으로 고정해 두면 문제 발생 시 안전한 버전으로 즉시 복구할 수 있습니다.

1. 채팅 히스토리에서 잘 작동하는 시점의 메시지 우클릭
2. **"Pin this version"** 클릭 → 이름 지정 (예: "로그인 기능 완성 v1")
3. 이후 문제 발생 시 해당 Pin으로 롤백 가능

**탈출 전략 — 접근법 전환**

3번 이상 같은 문제가 반복될 경우 다음 순서로 접근합니다:

```
Step 1: Chat Mode로 전환
   → "코드를 수정하지 말고, 이 문제의 근본 원인을 분석해 줘"

Step 2: 문제 재정의
   → 더 구체적인 재현 단계와 예상 동작을 새로 작성하여 전송

Step 3: 범위 축소
   → 문제가 있는 특정 컴포넌트 파일명을 명시하여 해당 파일만 수정 요청

Step 4: 수동 수정 (Dev Mode)
   → 유료 플랜: Code Mode에서 직접 해당 코드를 수정
   → 복잡하면 GitHub Export 후 로컬에서 수정
```

---

### 3) 크레딧 절약 10계명

|#|규칙|이유|
|---|---|---|
|1|매일 일일 크레딧(5개) 사용|당일 미사용분 소멸|
|2|Visual Edit으로 디자인 수정|크레딧 소비 없음|
|3|Chat Mode로 계획 먼저 논의|잘못된 구현 방지|
|4|한 번에 3~5개 변경만 요청|많을수록 오류 증가|
|5|기능 완성마다 Pin 저장|롤백 비용 절감|
|6|초기 PRD 작성에 시간 투자|재작업 방지|
|7|외부 AI로 프롬프트 사전 설계|첫 시도 성공률 향상|
|8|버그 3회 이상 반복 시 수동 수정 전환|AI 루프 방지|
|9|수정 금지 파일 명시|불필요한 수정 방지|
|10|Knowledge 최신 상태 유지|엉뚱한 수정 방지|

> ⚠️ **WARNING**
> 
> **"Try to Fix" 버튼을 3회 이상 반복하지 마세요.** 러버블의 자동 오류 수정 기능은 단순한 오류에는 유용하지만, 복잡한 오류에 반복 사용하면 코드가 점점 더 복잡해지고 AI 루프에 빠질 위험이 높아집니다. 3번 시도 후 해결이 안 된다면 반드시 Chat Mode로 전환하여 원인 분석을 먼저 요청하세요.

## 🔑 Key Takeaway

> **러버블에서의 성패는 프롬프트 품질에서 갈립니다. 좋은 프롬프트의 3요소(목적·맥락·제약)를 항상 포함하고, Knowledge를 프로젝트 두뇌로 활용하세요. 크레딧을 아끼는 가장 좋은 방법은 처음 프롬프트를 잘 작성하는 것입니다.**
> 
> 초기 PRD 작성 → Knowledge 설정 → 기능별 반복 수정 → 버전 Pin 저장의 사이클을 습관화하면 동일한 크레딧으로 훨씬 더 많은 것을 만들 수 있습니다.
