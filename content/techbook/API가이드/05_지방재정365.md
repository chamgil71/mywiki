# 5장. 지방재정365

> 공공 Open API 가이드북 — 2부. 공공기관·통합 정보 허브
> 확인 상태: 연혁·법적 근거 공식 페이지 다수 교차 확인, 인증 절차 확인, 개별 API는 지표별로 별도 등재(다수)됨을 확인, 세부 파라미터는 지표별 개별 확인 필요

### 0) 연결 고리 (Bridge)

2부에서 "공공기관·행정 인프라"를 다루는 마지막 장입니다. 4장(ALIO)이 개별 공공기관의 경영정보였다면, 이 장은 **지방자치단체와 그 산하 공공기관의 재정 데이터**를 다룹니다. 흥미롭게도 이 시스템의 역사를 보면 4장의 ALIO와 놀랍도록 닮은 패턴이 또 나타납니다 — "먼저 단순 공개 → 법으로 의무화 → 통합 플랫폼으로 재편"이라는 흐름입니다.

## 1) 개념 정의 및 필요성

### 1.1 20년에 걸친 지방재정 공개의 역사

**핵심 정의**: 지방재정365는 지방재정, 지방교육재정, 지방공공기관의 재정·경영정보를 한곳에 공개하는 행정안전부 플랫폼이며, 예산·결산·재정공시·재정지표 등을 Open API로 제공합니다.

이 시스템의 연혁을 시간순으로 보면:

- **2002년부터**: 당시 행정자치부가 "재정고"라는 이름의 시스템을 운영하며 지방재정 통합공시·통합재정개요·재정연감 등을 공개했습니다. 업무추진비, 부채 규모, 행사·축제 경비 등 **63종**의 재정정보를 지자체 간 비교 공시하는 게 목적이었습니다. 아직 법적 의무는 아니었던 시기입니다.
- **2006년부터**: 지방재정법 **제60조**에 근거해, 각 지자체가 자체 홈페이지를 통해 예산서·결산서를 매년 8월(2015년부터는 2월·8월 연 2회) 공시하는 게 법적 의무가 됩니다 — 다만 이건 **지자체별 개별 공시**입니다. 아직 한곳에 모아 비교할 수 있는 형태는 아니었습니다.
- **2010년부터**: 지방재정법 **제60조의2**에 근거해, 행정안전부가 여러 지자체의 공시 내용을 모아 매년 10월(2015년부터 4월·10월 연 2회) **통합공시**하기 시작합니다. "재정고"가 이 시점에 법적 근거를 갖춘 정식 통합공시 체계로 격상된 것으로 보입니다.
- **2015년 8월**: 지방재정통합공개시스템, 즉 지금의 "지방재정365" 구축이 시작됩니다.
- **2016년 5월 1일**: 정식 대국민 서비스가 개시됩니다. 이름의 "365"는 "1년 365일 어디서나 재정을 투명하게 공개한다"는 의미로 지어졌습니다. 이때 지방자치단체뿐 아니라 **지방공기업, 지방출자출연기관, 교육청**까지 연계해 통합 공개하는 게 핵심 특징으로 소개됐습니다. 초기 통합 대상은 1,288개 지자체·공기업·기관이었습니다.
- 서비스 개시 후 1년 만에 약 82만 명이 방문하는 사이트로 성장했고, 이후 매년 국민 만족도조사를 거쳐 서비스가 개선되고 있는 것으로 확인됩니다.

1장(법제처)과 4장(ALIO)에서 반복해서 본 패턴 — "먼저 사람이 보는 공개 시스템으로 시작 → 법이 의무화 → 나중에 통합·API화" — 이 여기서도 그대로 나타납니다. 다만 이 장은 그중에서도 **"통합"이라는 단계가 법 조문(제60조 vs 제60조의2)으로 명확히 분리되어 있다는 점**이 독특합니다 — 즉 "지자체가 각자 공개하는 것"과 "행정안전부가 모아서 비교 가능하게 하는 것"이 법적으로 완전히 다른 두 단계의 의무라는 뜻입니다.

### 1.2 왜 필요한가

지자체나 지방공기업을 다루는 프로젝트(2부의 다른 장들과 결합해 "이 지역 공공기관의 재정 건전성은?" 같은 분석)에서, 세입세출·재정자립도·통합재정운영표 같은 표준 지표를 API로 바로 가져올 수 있습니다. 1.1절의 역사를 알면, 이 데이터가 **왜 지자체마다 형식이 표준화되어 비교 가능한지**도 이해됩니다 — 애초에 "비교 공시"가 이 시스템의 존재 목적(2002년 재정고 시절부터)이었기 때문입니다.

## 2) 핵심 원리 및 구조

### 2.1 인증 절차 (공식 확인)

```mermaid
flowchart LR
    A["로그인"] --> B["OpenAPI 인증키 신청"]
    B --> C["OpenAPI 검색 및<br/>이용방법 확인"]
    C --> D["서비스 활용"]

```

> **NOTE**: 인증키는 **타인에게 양도할 수 없다**는 점이 공식 이용안내에 명시되어 있습니다. 여러 프로젝트에서 하나의 키를 공유하는 방식은 이용약관상 권장되지 않습니다.

### 2.2 API 구성 — 지표별 개별 등재 방식

지방재정365의 Open API는 하나의 통합 엔드포인트가 아니라, **지표(재정지표)마다 개별 API로 등재**되는 구조입니다(공식 데이터 확인). 이것도 1.1절의 역사와 무관하지 않습니다 — 애초에 "재정고" 시절부터 63종의 서로 다른 재정정보를 각각 별도 항목으로 관리해온 전통이, API 시대에도 "지표=API"라는 1:1 대응 구조로 그대로 이어진 것으로 보입니다. 확인된 API 예시:

| API명 | 내용 |
|---|---|
| 세입예산 | 자치단체별 세입총계, 회계별 세입액 (2012회계연도~) |
| 세입세출현황 | 우리 지자체 세입세출현황 |
| 통합재정운영표 | 복식부기 계정과목별 당기/전기 금액 및 증감율 (2015회계연도~) |
| 재정운용상황 개요 | 재정자립도·재정자주도·사회복지분야예산비율 등 (2016회계연도~) |
| 우리 지자체 재정공시 | 지방재정법 제60조 근거, 예산기준(2월)·결산기준(8월) 연2회 정기공시 링크 정보 |
| 재정자립도(최종) | — |
| 청사면적 | — |
| 지방교부세 인센티브현황 | — |

> **WARNING**: 이 표는 확인된 API 중 일부만 예시로 든 것입니다. 지표 수가 많고 계속 추가되므로, 실제 프로젝트에서는 3장의 공공데이터포털 검색 API로 `제공기관=행정안전부 지방재정보조금정보과` 또는 키워드 `지방재정365`로 먼저 전수 검색하는 것이 효율적입니다.

> **NOTE**: "우리 지자체 재정공시" API는 성격이 조금 다릅니다. 이건 재정 수치 자체가 아니라, **1.1절에서 본 지방재정법 제60조(개별 공시)에 따라 각 지자체 홈페이지에 게시된 재정공시 페이지의 링크 정보**를 제공합니다. 즉 이 장의 API에는 "제60조 통합공시 데이터"(수치 자체)와 "제60조 개별공시 링크"(어디를 찾아가면 되는지)가 섞여 있다는 뜻이므로, API를 고를 때 어느 쪽이 필요한지 먼저 구분해야 합니다.

### 2.3 URL 패턴 (공식 확인)

각 API는 아래와 같은 형태의 URL로 개별 접근합니다.

```
https://www.lofin365.go.kr/portal/LF5110000.do?pdtaId={지표별 고유ID}
```

`pdtaId`가 지표마다 다른 긴 영숫자 코드로 부여됩니다. API 유형은 지표에 따라 `LINK`(외부 링크형) 또는 `JSON+XML`(REST형)로 섞여 있는 것으로 확인됩니다 — 이것도 2.2절 NOTE에서 본 "링크 정보"와 "수치 데이터"의 구분과 맞물립니다.

## 3) 코드 예제 및 실행 환경

```python
# lofin365_client.py — 지표별 API 호출 템플릿
# v0.1, Python 3.11+
"""
NOTE: pdtaId별로 세부 요청 파라미터가 다를 수 있습니다.
      아래는 공통 골격이며, 실제 사용 전 해당 지표의 data.go.kr 상세페이지에서
      요청변수·출력결과 표를 개별 확인하십시오.
"""
import requests

BASE_URL = "https://www.lofin365.go.kr/portal/LF5110000.do"


def fetch_indicator(pdta_id: str, extra_params: dict | None = None, timeout: int = 10) -> str:
    """지표별 재정 데이터 조회. pdta_id는 data.go.kr 등재 페이지에서 확인."""
    params = {"pdtaId": pdta_id}
    if extra_params:
        params.update(extra_params)
    resp = requests.get(BASE_URL, params=params, timeout=timeout)
    resp.raise_for_status()
    return resp.text  # 지표에 따라 XML/JSON 혼재 — 실제 Content-Type 확인 후 파싱 분기


def is_link_type_response(content_type: str) -> bool:
    """2.2절에서 구분한 LINK형 vs JSON+XML형 응답을 Content-Type으로 판별하는 헬퍼."""
    return "text/html" in content_type or "text/plain" in content_type
```

## 4) 실무 시나리오

- **공공기관 vs 지방정부 재정 비교**: 4장(ALIO 기관정보)로 기관 목록을 얻고, 이 장으로 해당 기관·지자체의 재정 데이터를 결합. 1.1절에서 확인했듯 이 장의 데이터는 지방공기업·출자출연기관·교육청까지 연계되어 있으므로, 4장이 다루는 중앙 공공기관과는 상호 보완 관계입니다(4장=중앙정부 산하, 5장=지방자치단체 산하).
- **지역 분석 프로젝트**: 7부(공간·기상)·8부(지역 데이터)와 결합해 "이 지역의 재정 건전성 + 인구 + 공간정보" 통합 분석.
- **재정공시 링크와 수치 데이터를 함께 쓰는 경우**: "우리 지자체 재정공시" API(링크)로 원본 공시 페이지 위치를 확보하고, "통합재정운영표" 같은 수치형 API로 실제 분석용 데이터를 가져오는 조합이 유용합니다.

## 5) 트러블슈팅 & 주의사항

| 증상 | 원인 | 조치 |
|---|---|---|
| 원하는 지표의 pdtaId를 모름 | 지표별 개별 등재 구조(2.2절) | 3장 검색 API 또는 data.go.kr에서 "지방재정365" 키워드로 전수 검색 |
| 응답이 JSON이 아니라 XML/LINK | 지표마다 API 유형이 다름 | 호출 전 해당 지표의 데이터포맷(LINK/JSON+XML) 확인, 3.1절 `is_link_type_response`로 분기 |
| 통합공시 수치와 개별 지자체 홈페이지 수치가 다름 | 제60조(개별)와 제60조의2(통합)의 공시 시점 차이(1.1절: 개별은 8월 1회 또는 2·8월, 통합은 10월 1회 또는 4·10월) | 두 값을 비교할 때는 반드시 기준 시점(회계연도, 공시월)을 맞춰서 비교 |

## 6) 한 줄 요약

> 💡 **Key Takeaway**: 지방재정365는 하나의 API가 아니라 2002년 "재정고"부터 이어진 **재정지표마다 개별 등재된 API의 모음**입니다. "지자체 개별 공시"(지방재정법 제60조)와 "행정안전부 통합공시"(제60조의2)라는 서로 다른 법적 근거를 가진 두 갈래 데이터가 섞여 있다는 걸 알면, API를 고를 때 헤매지 않습니다.
