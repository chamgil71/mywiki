# 제29장. 주의사항과 함정

> *"AI는 강력하다. 그래서 더 신중해야 한다."*

---

### 0) 연결 고리 (Bridge)

이 책의 마지막 장입니다. 지금까지 바이브코딩과 에이전트 코딩의 무한한 가능성을 보여드렸습니다. 마지막으로는 반드시 알아야 할 위험과 함정을 솔직하게 다룹니다. AI 도구의 한계를 이해하는 것은 도구를 더 잘 사용하는 것이지, 사용하지 말라는 것이 아닙니다.

---

### 1) 함정 1 — AI 출력을 검증하지 않고 사용

#### 증상과 사례

```
사례 1 — 수치 오류:
  AI가 보고서에서 "2025년 AI 시장 규모는 4.7조 달러"라고 작성
  → 실제: 4,700억 달러 (단위 오류, 10배 과장)
  → 결재자가 오류를 발견하지 못하고 공식 보고서에 포함

사례 2 — 존재하지 않는 API:
  AI가 생성한 코드에 pdfplumber.Table.get_spans() 사용
  → 실제로 없는 메서드 → 코드 실행 즉시 AttributeError
  → 배포 후에 발견 → 긴급 수정 필요

사례 3 — 법령 오류:
  AI가 "개인정보보호법 제23조에 따르면..."이라고 인용
  → 조문 번호가 틀렸거나 최신 개정 내용 미반영
  → 법적 문서에 오류가 그대로 포함
```

#### 검증 원칙

```
수치·날짜 → 반드시 1차 출처 확인
  AI가 제시한 수치를 그대로 쓰지 말고
  해당 수치의 출처(보고서, 공시, 공문서)를 직접 확인

코드의 라이브러리·메서드 → 실행 전 확인
  "이 코드에서 사용한 라이브러리와 메서드가
   실제로 존재하는지 확인해줘"라고 AI에게 재확인 요청

법령·정책 → 공식 문서 대조
  국가법령정보센터(law.go.kr) 또는
  해당 기관 공식 문서와 반드시 대조

고유명사·관계 → 직접 검색
  회사명, 인물, 제품명의 관계는
  공식 웹사이트나 위키피디아로 확인
```

### 2) 함정 2 — 과잉 신뢰와 책임 분산

#### 위험한 사고방식

```
"AI가 만들었으니까 내 책임은 아니다"
→ AI 출력물의 법적·도덕적 책임은 항상 사용자에게 있습니다.
  AI는 도구이지 책임 주체가 아닙니다.

"AI가 더 잘 알겠지"
→ AI는 학습 데이터 기반의 확률적 추론 도구입니다.
  내 업무 맥락, 조직 문화, 법적 요건은
  AI가 알 수 없습니다. 그것을 아는 것은 나입니다.

"AI가 틀릴 리 없어"
→ 최신 모델도 틀립니다. 특히 한국어 도메인 전문 지식,
  최신 정보(학습 데이터 이후), 수치 계산에서 오류가 납니다.
```

#### 인간 감독(Human Oversight) 원칙

```
AI가 직접 실행할 수 있는 작업일수록
사람의 확인이 더 중요합니다.

감독이 반드시 필요한 영역:
  □ 금전이 관련된 결정 (예산, 계약, 지출 승인)
  □ 개인정보 처리 (수집, 저장, 삭제)
  □ 법적 효력이 있는 문서 (계약서, 공문, 신청서)
  □ 의료·안전 관련 정보
  □ 외부 공개 콘텐츠 (보도자료, 공식 발표)
  □ 운영 DB의 데이터 수정·삭제
```

### 3) 함정 3 — 보안과 개인정보 노출

#### 가장 흔한 실수

```
실수 1 — API 키를 GitHub에 올리기:
  .env 파일을 .gitignore에 추가하지 않으면
  GitHub 공개 레포에 API 키가 노출됨
  → 수 분 내 악용 (비용 폭탄, 서비스 남용)
  예방: 프로젝트 시작 시 첫 번째로 .gitignore 설정

실수 2 — 고객 개인정보를 AI에 입력:
  이름, 전화번호, 주민번호, 계좌번호가 포함된
  파일을 Claude.ai에 첨부
  → AI 서비스 데이터 처리 정책에 따라 저장될 수 있음
  예방: 개인정보는 마스킹 후 입력 (홍길동 → 홍OO)

실수 3 — 기밀 사업 정보를 공개 AI에 입력:
  미공개 제품 로드맵, 미발표 실적, 인수합병 정보
  → 데이터 보안 정책 위반, 기밀 유출 위험
  예방: 기밀 정보는 내부 배포 모델(로컬 Ollama) 사용

실수 4 — Supabase service_role 키 노출:
  클라이언트 코드에 service_role 키 사용
  → 브라우저에서 접근 가능 → DB 전체 노출
  예방: service_role은 서버 전용, 클라이언트에는 anon 사용
```

#### 보안 체크리스트

```
코드 공개 전 필수 확인:
  □ .gitignore에 .env 포함 여부
  □ 코드에 하드코딩된 API 키 없음
  □ Supabase anon/service_role 올바른 위치에 사용
  □ 로그에 개인정보 출력 없음
  □ SQL 쿼리에 사용자 입력 직접 삽입 없음 (SQL Injection)

AI 서비스 사용 전 확인:
  □ 입력 데이터에 개인정보 없음
  □ 회사 기밀 정보 포함 여부 확인
  □ 조직의 AI 활용 정책 준수 여부
```

### 4) 함정 4 — 맥락 소실과 일관성 붕괴

#### 증상

```
대화가 길어질수록 AI가:
  - 이전에 정한 규칙을 무시하기 시작함
  - 초반에 결정한 데이터 구조와 다른 코드를 생성
  - "httpx 쓰라고 했는데" requests를 다시 사용
  - 프로젝트 폴더 구조를 바꿔버림
```

#### 해결책

```
예방:
  □ SKILL.md를 대화 시작 시 항상 첨부
  □ Claude Projects에 SKILL.md 등록
  □ 20회 이상 대화 후 새 대화창 시작

감지:
  AI 출력물에서 다음이 보이면 맥락 소실 신호:
  - import requests (httpx 쓰기로 했으면)
  - print() (logging 쓰기로 했으면)
  - 폴더 경로가 SKILL.md와 다름

복구:
  "[SKILL.md 재첨부]
   방금 코드에서 SKILL.md 규칙 위반이 있어.
   위반 항목: [구체적 목록]
   수정해줘."
```

### 5) 함정 5 — 버전 관리 없이 에이전트 실행

#### 사고 사례

```
시나리오:
  claude --dangerously-skip-permissions 실행
  → "전체 리팩터링해줘"
  → AI가 30개 파일을 수정
  → 결과가 마음에 안 들지만 원본이 없음
  → 전체 프로젝트를 처음부터 다시 작성

예방:
  에이전트 실행 전 반드시:
  git add . && git commit -m "에이전트 실행 전 백업"

복구:
  git checkout .        # 모든 변경 취소 (커밋 전)
  git reset --hard HEAD~1  # 마지막 커밋 되돌리기
```

### 6) 함정 6 — 자동화 과잉 의존

#### 역설적 위험

```
자동화가 잘 될수록 생기는 문제:

문제 1 — 블랙박스화:
  "n8n이 알아서 해주니까" → 실제 로직을 이해 못 함
  → 오류 발생 시 원인 파악 불가
  → 자동화 시스템이 멈추면 완전히 무력화

문제 2 — 단일 장애점:
  모든 업무가 n8n 하나에 의존
  → 서버 다운 → 모든 업무 마비
  예방: 핵심 업무는 수동 대안 프로세스 유지

문제 3 — 품질 감각 저하:
  AI가 항상 대신 써주다 보면
  스스로 글쓰기·분석 능력이 퇴화할 수 있음
  예방: AI는 "초안 도구"로만 활용, 최종 검토·수정은 직접

문제 4 — 의존성 잠금:
  특정 AI 서비스에 과도하게 의존
  → 가격 인상, 서비스 종료 시 대안 없음
  예방: 로컬 모델(Ollama) 병행 유지
```

### 7) 함정 7 — AI 생성 코드의 보안 취약점

#### 흔한 보안 취약점 패턴

```python
# AI가 생성할 수 있는 위험한 패턴 예시

# 취약점 1 — SQL Injection
# AI가 종종 이렇게 생성함:
query = f"SELECT * FROM users WHERE name = '{user_input}'"
# user_input에 "'; DROP TABLE users; --" 입력 시 재앙

# 올바른 방법:
query = "SELECT * FROM users WHERE name = ?"
cursor.execute(query, (user_input,))

# 취약점 2 — 하드코딩된 비밀번호
API_KEY = "sk-ant-api03-실제키값"  # AI가 가끔 예시를 실제처럼 작성
# 올바른 방법:
API_KEY = os.getenv("ANTHROPIC_API_KEY")

# 취약점 3 — 경로 순회 (Path Traversal)
file_path = f"/data/{user_filename}"  # ../../../etc/passwd 가능
# 올바른 방법:
file_path = Path("/data") / Path(user_filename).name  # 파일명만 추출
```

#### AI 코드 보안 검토 요청

```
AI가 코드를 생성하면 보안 검토도 요청합니다:

"방금 생성한 코드에서 다음을 확인해줘:
 □ SQL Injection 가능성
 □ 하드코딩된 비밀번호나 API 키
 □ 사용자 입력이 파일 경로에 직접 사용되는 부분
 □ 민감 정보가 로그에 출력되는 부분
 □ 외부 입력 검증 없이 처리하는 부분"
```

### 8) 함정 8 — 비용 관리 실패

```
예상치 못한 API 비용 발생 사례:

사례 1 — n8n 루프 버그:
  오류로 인해 같은 API를 10,000번 반복 호출
  → Claude API 비용 수백 달러 청구
  예방: n8n 워크플로우에 실행 횟수 제한 노드 추가

사례 2 — 대용량 파일 반복 처리:
  100MB PDF를 테스트마다 전체 파싱
  → API 토큰 비용 급증
  예방: 개발 시 소형 샘플 파일 사용

사례 3 — 무한 에이전트 루프:
  Claude Code 자율 모드에서 오류 수정 루프가 무한 반복
  예방: 에이전트 최대 실행 시간 설정, 비용 알림 설정

비용 모니터링:
  Anthropic Console → Usage → 일별 비용 확인
  월 예산 설정 → 초과 시 알림
  Claude Code: /cost 명령으로 현재 세션 비용 확인
```

### 9) 올바른 AI 협업 마인드셋

```
AI는 강력한 도구입니다.
망치가 강력할수록 잘못 쓰면 더 큰 피해를 줍니다.

올바른 마인드셋:

AI = 빠른 초안 작성자
  → 내가 검토하고 수정하는 것이 최종 산출물

AI = 지식 보조자
  → AI의 지식에는 시간 제한, 오류, 편향이 있음
  → 중요한 판단은 나의 도메인 지식과 경험이 우선

AI = 자동화 엔진
  → 반복 작업을 없애주지만
  → 자동화된 오류도 반복됨 → 검증 필수

AI = 학습 파트너
  → AI가 만든 코드를 읽으면서 새로운 패턴을 배울 수 있음
  → 수동적으로 받기만 하면 성장이 없음
```

### 10) 마지막 한 마디

이 책에서 다룬 모든 도구와 기법은 빠르게 발전하고 있습니다. 특정 도구의 사용법은 6개월 후 달라질 수 있습니다. 하지만 변하지 않는 것이 있습니다.

```
변하지 않는 것:

1. 명확한 요구사항이 좋은 결과를 만든다
2. 결과는 반드시 검증해야 한다
3. 오류에서 배운 규칙이 쌓이면 실력이 된다
4. 재사용 가능한 자산이 시간을 절약한다
5. AI는 도구이고, 책임은 사람에게 있다

이 다섯 가지만 기억한다면,
어떤 새로운 AI 도구가 나오더라도
빠르게 적응하고 활용할 수 있습니다.
```

### 11) 한 줄 요약

> 💡 **Key Takeaway:** AI 도구의 함정은 **과잉 신뢰, 보안 소홀, 버전 관리 부재, 맥락 소실, 비용 무관리** 다섯 가지로 수렴하며, 이 모든 함정의 해결책은 결국 하나입니다 — **AI를 강력한 조수로 신뢰하되, 최종 검토와 책임은 항상 사람이 진다.**
